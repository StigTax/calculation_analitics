# Аналитика логов калькуляторов (Saint-Gobain)

Скрипт обрабатывает выгрузку логов действий пользователей на калькуляторах
(`calc.saint-gobain.ru`, `hub.saint-gobain.ru`, `vetonit.com`) и строит
Excel-отчёт с таблицами и графиками: топ пользователей по скачиваниям,
уникальные активности по регионам, конверсия «заход → скачивание»,
динамика сессий по месяцам и округам.

## Входные данные
 
Excel-файл (`.xlsx`) с листом **«Статистика»**, содержащим колонки:
 
| Колонка | Назначение |
|---|---|
| `Время отчета` | дата-время действия, формат `дд-мм-гггг чч:мм:сс` |
| `Калькулятор` | название калькулятора |
| `Действие` | `Открыта страница калькулятора` / `Пользователь скачал отчет` |
| `Страница калькулятора` | URL, из него извлекается домен |
| `IP адрес`, `Uuid`, `ID отслеживания` | технические идентификаторы |
| `Регион`, `Город` | геоданные пользователя |
| `Пользователь, совершивший действие` | логин (может быть пустым) |

### Конфиги-исключения
 
- `config/excluded_users.csv` (создаётся из `.example`) — колонка
  `users`, список логинов, которые нужно выкинуть из аналитики
  (сервисные/тестовые аккаунты).
- `config/excluded_domains.csv` (создаётся из `.example`) — колонка
  `domain`, список доменов (без `http://` и без слэша в конце).
Оба файла обязательны для запуска через `main.py` — без них `load_clean_data`
упадёт.

## Запуск

```bash
python -m main <путь_к_файлу.xlsx> [опции]
```

**Опции:**
 
| Флаг | Описание |
|---|---|
| `--output PATH` | путь к итоговому xlsx. По умолчанию — автогенерация в `output/` по калькулятору и периоду данных |
| `--months-back N` | последние N месяцев от самого позднего месяца в данных (по умолчанию 6) |
| `--period START END` | явный диапазон месяцев, например `--period 2026-07 2026-09` |
 
`--months-back` и `--period` взаимоисключающие.

**Примеры:**

```bash
# последние 6 месяцев (значение по умолчанию)
python -m main "C:/Downloads/statistics.xlsx"

# только за конкретный квартал
python -m main "C:/Downloads/statistics.xlsx" --period 2026-07 2026-09

# свой путь для отчёта
python -m main "C:/Downloads/statistics.xlsx" --output "reports/q3.xlsx"
```

**Напрямую, без CLI** (путь к файлу и период берутся из констант/дефолтов),
дополнительно дублирует все таблицы в консоль (включая сравнительные,
с листа «Сравнение»):

```bash
python -m src.analytics.aggregate
```

## Что попадает в отчёт
 
Первый лист — **«Пояснительная записка»**: разъяснение по каждой
метрике отчёта (что это, как считается) плюс наглядная схема пути от
сырых событий лога до итоговых цифр конверсии и скачиваний.
 
Дальше — отдельный лист на каждый домен (`calc`, `hub`, `vetonit`):
 
1. **Топ пользователей по скачиваниям** — за всё время и за последние
   30 дней от момента запуска отчёта. Считается только для
   `calc.saint-gobain.ru`.
2. **Активности по региону** — уникальные пользователи/сессии в разрезе
   федерального округа.
3. **Конверсия** — доля сессий с заходом, закончившихся скачиванием,
   по каждому калькулятору.
4. **Конверсия по месяцам** — та же конверсия, что в п.3, но в
   динамике по месяцам, с line-графиком.
5. **Количество скачиваний по калькулятору** — сырые события скачивания
   (не сессии): пользователь, скачавший отчёт 5 раз за визит, даёт 5,
   а не 1. Другая единица измерения, чем в «Конверсии» — подробнее на
   листе «Пояснительная записка».
6. **Скачивания по месяцам** — то же самое, в динамике по месяцам.
7. **Сессии по месяцам** — количество сессий по калькуляторам, с графиком
   динамики.
8. **Сессии по месяцам и округам** — та же разбивка + округ. При 4+
   месяцах в таблице вместо графика используется heatmap (иначе график
   становится нечитаемым).
Плюс отдельный лист **«Сравнение»** — кросс-сайтовые таблицы, не
привязанные к одному домену:
 
9. **Сравнение конверсии между сайтами.**
10. **Динамика количества сессий по сайтам.**
11. **Сравнение количества скачиваний отчётов.**

### Названия таблиц и графиков

Заголовок каждой таблицы и графика (кроме листа «Сравнение») собирается
по шаблону:

```
{Название метрики} - {Калькулятор} - {Сайт} - от {дата}
```

например: `Топ пользователей - Калькулятор СФТК (Розничный) - Платформа
калькуляторов - от 15.09.2026`. На листе «Сравнение» часть `{Сайт}` не
подставляется — там сравниваются все сайты сразу.

- **Сайт** — человекочитаемое имя из `SITE_LABELS` (`constants.py`),
  подставляется вместо служебного ключа (`calc`/`hub`/`vetonit`);
  последний остаётся только в названии вкладки листа.
- **Калькулятор** — берётся из сырых данных, но некоторые названия
  неоднозначны (например, «Калькулятор СФТК» без уточнения путается
  с «Калькулятор СФТК (Проектный)») — такие случаи прописаны в
  `CALCULATOR_DISPLAY_OVERRIDES` (`constants.py`) и подменяются на явный
  вариант, например «Калькулятор СФТК (Розничный)».
- **Дата** — дата самой свежей записи в переданном в отчёт логе
  (`get_report_date`, `reports/utils.py`), не момент запуска скрипта. Если
  отчёт построен по обрезанному периоду (`--months-back`/`--period`),
  дата отражает конец этого периода, а не всего исходного файла.

## Важные детали логики (чтобы не удивляться цифрам)

- **Сессия** — действия одного `Uuid` без разрыва больше 30 минут
  (`SESSION_GAP_MINUTES` в `constants.py`). Порог подобран по 90-му
  перцентилю реальных пауз.
- **identity** для подсчёта уникальных: логин, если он указан и домен
  главный (`calc.saint-gobain.ru`), иначе — `Uuid`.
- Если регион не найден в справочнике округов (`FEDERAL_DISTRICTS`),
  он попадает в бакет «Не определён», а сам регион печатается в консоль —
  это сигнал дополнить справочник в `constants.py`.
- Окно «последние 30 дней» считается от **текущего момента запуска**
  скрипта, а не от последней даты в логе.
- «Топ за всё время» / «топ за 30 дней» не зависят от `--months-back` /
  `--period` — эти флаги управляют только таблицами по сессиям.

## Известные ограничения

- Формат даты в исходнике жёстко задан (`%d-%m-%Y %H:%M:%S`) — при смене
  формата выгрузки скрипт упадёт с ошибкой парсинга.
- Если пользователь возвращается на уже открытую страницу спустя долгое
  время и сразу скачивает отчёт, такая сессия может не содержать событие
  «Открыта страница» — учитывается отдельно как «Скачивание без захода»
  и не участвует в проценте конверсии.
- В `src/analytics/aggregate.py` есть собственный блок `__main__` для быстрого
  локального запуска (`python -m src.analytics.aggregate`) с путём к файлу,
  зашитым в `RAW_FILE` (`constants.py`). Он используется для отладки и
  не совпадает по логике периодов с `main.py` — для боевых отчётов
  используйте `main.py`.
- `python -m src.analytics.aggregate` дублирует все таблицы в консоль через
  `print_results` (включая лист «Сравнение»). `main.py` этого не делает —
  там только запись в xlsx, без вывода в терминал.

### Среднее время сессии (обсуждается, решение не зафиксировано)

Запрошена метрика "среднее время сессии". Длительность сессии = разница

измерить при текущей схеме трекинга нет — нет явного события "выхода").
На созвоне предполагается предложить **медиану вместо среднего**
(устойчивее к редким аномально длинным сессиям) — ждём подтверждения
группы, в ToDo как решённое пока не заносим.
Отдельно стоит учесть: у медианы есть своё слепое пятно, не то же самое,
что у среднего — если много сессий состоят из одного действия
(длительность 0 по построению: скачивание без захода, либо мгновенный
уход), они могут утащить медиану к нулю. Предлагаемое решение — считать
медиану только по сессиям с более чем одним действием, а долю
"нулевых" (одно действие) сессий показывать отдельной цифрой рядом, не
смешивая с самой медианой.
 
### Новое отслеживаемое действие "Сформирован расчёт" (заблокировано, срок неизвестен)

Предложено начать логировать в поле "Действие" ещё и факт формирования
расчёта — обязательный шаг перед скачиванием, механика в калькуляторах
уже есть, скачать без него нельзя. Ждём реализации на стороне трекинга,
срока пока нет — не начинать эту часть, пока действие реально не
появится в выгрузке.
 
Что это даст, когда появится:
- Частично устранит проблему "нулевых" сессий для медианы длительности
  (см. выше) — у части сессий без второго события появится вторая
  точка для измерения интервала.
- Позволит разложить конверсию на два перехода вместо одного: "зашёл →
  сформировал расчёт" и "сформировал → скачал", вместо одной сквозной
  цифры "зашёл → скачал". Это покажет, на каком именно шаге теряются
  пользователи, а не только сам факт потери.
На что это повлияет технически, когда дойдёт очередь:
- `ACTIONS`/`ACTION_VISIT`/`ACTION_DOWNLOAD` в `constants.py` сейчас
  жёстко рассчитаны на ровно два значения; `conversion_rate` делает
  `reindex(columns=ACTIONS)` именно под эту пару — добавление
  действия потребует пересмотра самой функции (два перехода вместо
  одного), не просто добавления строки в список.
- Переходный период: старые выгрузки не будут содержать новое действие
  вообще — метрики на его основе должны для старых месяцев явно
  показывать "нет данных", а не молча считать как 0/провал.

### Явное закрытие сессии по неактивности (заблокировано, срок неизвестен)

Предложено на стороне сайта фиксировать принудительное закрытие сессии,
если после последнего действия прошло ~15 минут — то есть явный
маркер конца сессии вместо реконструкции по разрыву между действиями
(как сейчас в `add_session_id`).
 
Важная ловушка в реализации, если делать "в лоб": если событие
"сессия закрыта" шлётся строго через фиксированный тайм-аут после
последнего действия — ВСЕ такие сессии получат длительность, примерно
равную этому тайм-ауту (15 минут), независимо от реального поведения.
Сессия с одним действием, у которой раньше была честная длительность 0
(видимый артефакт, легко отфильтровать), превратится в "15 минут",
выглядящих как настоящая вовлечённость — искажение той же метрики
(медиана времени сессии), только в менее заметной форме, чем сейчас.
 
Более честная альтернатива — периодический heartbeat через Page
Visibility API, пока страница реально видима/в фокусе (каждые
30-60 сек), а не единичное событие по тайм-ауту: тогда последний
полученный heartbeat — это реальная оценка вовлечённости, а не
константа. Дороже в реализации на фронте (регулярная отправка, а не
одно событие), но не искажает данные искусственно.
 
В любом случае не заменяет полностью текущую реконструкцию сессий по
разрыву между действиями (Uuid + 30 мин) — явное закрытие не сработает
при резком закрытии вкладки/потере сети/креше браузера
(`beforeunload` не гарантирован), так что текущий метод остаётся
нужен как минимум как резервный.

## История решений

Единица измерения для "количество скачиваний" зафиксирована: считаем
**все действия скачивания** — сырые события (`.size()`, как в
`top_downloaders`), не сессии и не уникальных людей. Один человек,
скачавший 5 раз за визит, даёт 5. Это другая единица, чем у конверсии
(там — сессии, пересечение множеств) — разница зафиксирована на листе
**«Пояснительная записка»** (первый лист отчёта).

**Сделано:**
- Лист «Сравнение» с тремя кросс-сайтовыми таблицами (конверсия,
  сессии по месяцам, количество скачиваний — все три в разбивке по
  калькулятору и сайту), плюс лист «Пояснительная записка» (первый
  лист отчёта).
- Конверсия по месяцам, для каждого сайта (по калькуляторам внутри
  сайта) — на пересечении множеств визит/скачивание из
  `conversion_rate`, с помесячной группировкой сессий.
- Количество скачиваний отчёта по месяцам, для каждого сайта —
  группировка сырых событий `ACTION_DOWNLOAD` по (`Калькулятор`,
  `Месяц`), без привязки к сессиям.
